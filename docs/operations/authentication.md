# Authentication and credential custody

Cloudflare Access admits operators; account authorization installs/administers
resources; private bindings connect runtime services. An app login does not
grant Cloudflare account administration. Each installation must generate its
own Access issuer/audience and allowed-email policy.

## Application and runtime

The Worker cryptographically verifies the edge-issued Access JWT signature,
issuer, audience and expiry with JOSE. Arbitrary bearer text does not replace
that check. Browser mutations and WebSocket upgrades reject foreign origins.
Admitted operators share the installation's work; this is not tenant isolation.

The gateway's default public HTTP handler returns 404 and production configs
disable workers.dev/previews. Toolbox capabilities are supplied through the
ToolboxGateway service binding, with generation and operation-ownership checks.
The app and gateway have model/tool secrets, not account-admin API credentials.

OpenCode keys belong in Cloudflare Worker Secrets (or supported Secrets Store
bindings), entered through native Dashboard/CLI prompts. Optional BYOK provider
keys stay in OpenCode. Target API credentials have a separate audience-bound
storage/use path. Do not put credentials into prompts, Git or source config.

## Installation authorization

The installer requires an explicitly selected account and config/state location.
Use official cf auth login; do not scrape any CLI credential cache. cf and
Wrangler logins are distinct. Account token provisioning and appropriate product
roles are required; a login alone does not establish entitlement.

The native authorization adapter creates a two-hour account-scoped deployment
lease with the needed product permissions, holds its value in process memory
and child environment, and revokes it in finally. It grants no token-management
permission to the lease itself. A supplied CI token stays caller-owned. An
interrupted process may leave a lease until expiry; reconcile native token
metadata before retrying a create, and never log token responses.

Required roles are Account Settings Read, Workers Scripts Write, Workers
Containers Write, Artifacts Write, Access Apps and Policies Write, and Access
Organizations/Identity Providers/Groups Read. Resolve their current native
permission-group names/scopes rather than copying historical IDs.

Artifacts binding, REST and Git credentials have separate platform permissions.
Successful Worker deployment does not prove Artifacts token support. Report an
account-owned-lease rejection as a blocker; never broaden to a global key or
reuse the creator's credentials to work around it. Validate this path in the
selected account before treating fresh installation as accepted.

Use cloudflared access login --quiet for the app origin. The native client owns
its session cache/refresh; the installer captures token output privately and
sends it only to the selected HTTPS app API, with no redirects. State records
resource ownership and generated nonsecret configs, never model/Access secrets.

## Local defaults

The repository's Wrangler examples have empty trusted Access issuer/audience
and cannot authenticate a production user. Production config is generated by
the guided installer for the selected account. Never copy a personal deployment
config or run the installer against an account you have not reviewed.

For browser QA, the explicit runner uses a temporary native Access service token
and exact-token policy, preserving existing policies and revoking owned access.
See [browser QA](browser-qa.md); it is a test-only workflow, not an app login
bypass or a permanent public browser-control service.
